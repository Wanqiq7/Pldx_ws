# 导航力控 MPC 问题说明

## 范围与状态

本文记录截至 2026-11-01 当前工作树中的力控 MPC、轨迹交接和仿真实测结果。当前工作树包含尚未提交的规划器连续性交接修改，以及仿真力上限修改；它们不等同于已完成实车验证的版本。本文列出已发现的问题和主要风险，不声称穷尽所有故障。

核心结论：**常规热重规划的轨迹交接连续性已有改善，但冷启动、方向变化和力指令尖峰仍未解决。不能仅凭目标到达判定控制稳定。**

证据分级：

- **已测**：本会话中在指定仿真条件下采集到的现象，仅代表对应运行。
- **代码事实**：当前实现明确具有的行为，不等于已经造成实测故障。
- **待验证**：有代码或观测支持，但尚未隔离因果关系的风险。

## 数据与控制链

```text
Point-LIO /aft_mapped_to_init + TF
               |                       MINCO /opt_path
               +----------> 力输入 MPC <-----------+
                              |
               /chassis_cmd_mpc: Fx, Fy, Mz
                      /                   \
       仿真适配器 /sim/cmd_force          ros2_libxr
                |                        |
      Gazebo MecanumDrive2          USB / 底盘控制器
```

- 规划器发布采样轨迹 `/opt_path`；控制器构造状态 `[x, y, yaw, vx, vy, omega]`，分别求解平移和偏航 QP，发布首步平面力和偏航力矩。代码：[MPC 控制器](../../src/navigation/minco_controller/src/minco_mpc_controller.cpp)、[QP 求解器](../../src/navigation/minco_controller/src/dynamic_mpc_solver.cpp)、[消息定义](../../src/ros_interfaces/msg/ChassisCommand.msg)。
- 力指令在全局参考坐标系中发布，仅支持 `wrench.force.x/y` 和 `wrench.torque.z`。消息单位分别为 N 和 N·m；`force.z`、`torque.x/y` 不参与此平面模型。
- 仿真适配器将力旋转到车体系并发布 `/sim/cmd_force`；Gazebo 力模式直接作用在刚体，超时或无效输入归零。参见[仿真适配器](../../src/nav-simulation/sentry_simulation/sentry_simulation/cmd_vel_adapter.py)和 [MecanumDrive2](../../src/nav-simulation/sentry_simulation/plugins/mecanum_drive2/MecanumDrive2.cc)。仿真不等价于实车轮力分配、电机与功率限制。
- 实车由 [ros2_libxr](../../src/navigation/ros2_libxr/src/ros2_libxr/src/ros2libxr.cpp) 处理时间戳、姿态和坐标转换，再发送至底盘。完整协议与固件边界见[力控集成说明](README.md)。

## 已测现象

### 轨迹切换附近的力尖峰

在 `RMUC_2025`、`robot_model:=real` 仿真中，使用当前会话配置的平面合力上限 100 N、偏航力矩上限 100 N·m，观察到新轨迹到达后数毫秒内出现较大的相邻控制周期力变化。一次采样中力由 `(-79.5, -51.1) N` 变为 `(11.9, -17.9) N`，矢量差约 97 N；另一次轨迹起始参考加速度从约 `(0.22, 0.31)` 变为 `(-1.08, -1.31) m/s²`。这是多次试验中的具体样本，不代表所有尖峰均有相同原因。

同一路线的单次往返对照，目标依次为 `(4.6, 8.3)` 和 `(5.7, 9.68)`，每个目标结束后等待约 1 秒读取 Gazebo 真值：

| 指标 | 修改前 | 当前连续性交接版本 |
| --- | ---: | ---: |
| 统计的参考切换次数 | 10 | 8 |
| 切换附近平面力相邻样本变化，中位数 | 26.2 N | 10.5 N |
| 切换附近平面力相邻样本变化，最大值 | 85.7 N | 166.2 N |
| 两段真值终点误差 | 0.054 / 0.059 m | 0.026 / 0.039 m |
| 两段导航结果 | 成功 / 成功 | 成功 / 成功 |

采样脚本分别按机器人附近的离散轨迹点估算新旧参考，在切换前后 ±0.15 个仿真秒内统计相邻力样本变化。它并非 MPC 内部投影状态的精确记录；两次运行的切换次数、路径和时序也不同，最大值尤其不能作为严格的统计对照。连续热拼接的多次切换在估算位置处的 P/V/A 差接近零；冷启动切换仍出现明显跳变。原始临时采样文件未保存在仓库中，以上数字仅为会话记录，后续应重新采集可归档数据。

**结论**：热交接机制改善了部分切换，但最坏力跳变没有得到证明或改善，仍需处理其他路径和控制环节。

### 到点后继续运动

一次 `real` 仿真往返中，Nav2 报告成功后车辆继续旋转，最终 Gazebo 真值航向约 `-1.0 rad`。定位与真值的旋转趋势基本一致。该次未记录同一时刻的 GoalChecker 输入和完整状态，**提前成功的具体原因尚未确认**。

相关代码事实：

- [sentry1.yaml](../../src/navigation/navi2_bringup/params/sentry1.yaml) 使用 `StoppedGoalChecker`，位置容差 0.1 m，角度容差 6.28 rad，允许几乎任意终点朝向；仍配置了平移和旋转停止速度阈值。
- 控制器在成功、取消、失效等情况下输出零力矩。零力不是主动制动；仿真力模式的行为见 `MecanumDrive2::PreUpdate`，实车同样不能把零力直接等同于车辆已经停稳。
- 应同步记录成功判定时间、GoalChecker 接收的速度、LIO 时间戳、真值角速度及最终惯性运动，再判断是否存在误判、延迟或制动能力问题。

### 点云与里程计延迟

早期运行时，原始 Gazebo 雷达数据与 `/clock` 相差约 0.01–0.05 s，而点云适配器输出扫描结束时间落后约 0.6–0.7 s，里程计和点云相应延迟约 0.4–0.75 s，超过 MPC 0.3 s 里程计超时，控制输出为零。

当时重建的仿真包未启用 Release 优化：适配器输出约 1.2 Hz，输入约 10 Hz。改用 Release 构建后，另一轮仿真里程计延迟约 0.10–0.14 s，控制器恢复非零力输出且短距离目标成功。这次未优化构建由本次排查过程引入，不应归因于算法本身。RViz 的 TF 消息过旧提示还可能涉及不同变换的时间范围，未单独证明其全部原因。

## 问题与代码

### 1. 新旧轨迹交接并非始终连续

**状态：已测；部分改善，仍未关闭。**

[局部重规划](../../src/navigation/minco_planner/src/minco_core/minco_planner.cpp) 当前在热启动时寻找车辆附近的旧轨迹，保留旧位置和偏航前缀，并从未来交接点的 P/V/A 生成新段；拼接结果经过轨迹验证，提交时检查交接是否过期及候选碰撞。相关入口为 `ReplanLocal`、`pollPlanResult` 和 `validateTrajectory`。

当旧轨迹剩余时间不足、轨迹方向与新路径差异大、离车过远、连接段不安全或缺少必要数据时，仍可能转冷启动。冷启动由当前位置和当前速度构造初始状态，加速度初始化为零，因此不能保证与旧参考连续。掉头时简单强制沿旧方向拼接，会产生空间重叠的往返轨迹；一次试验中最近点可能选中相反方向的轨迹分支，力峰值增大，因此该放宽已撤回。

当前方案还需验证动态障碍、急转、短轨迹和长时间跟踪落后等场景；不能仅根据一次短路线判断稳定性。

### 2. 最近点投影可能在重叠轨迹间切换

**状态：代码事实；对抖动的实际贡献待验证。**

[prepareReference](../../src/navigation/minco_controller/src/minco_mpc_controller.cpp) 每周期扫描当前参考轨迹并按欧氏距离选择最近点，再在相邻采样点投影。该选择没有对轨迹进度施加单调或时间连续约束。轨迹自交、掉头重叠、短时回退或车辆落后时，空间上接近的点可能对应不同运动方向，进而改变参考速度和加速度。

需要构造可重复的重叠轨迹测试，并同时记录 MPC 实际选用的索引、轨迹 ID、参考状态和输出；仅比较两条轨迹的第一个采样点不能证明该现象。

### 3. 参考前馈和输入变化率约束

**状态：代码事实；与轨迹切换尖峰的时间关联已测，不能解释全部尖峰。**

[dynamic_mpc_solver.cpp](../../src/navigation/minco_controller/src/dynamic_mpc_solver.cpp) 以相邻参考速度差除以预测步长计算参考加速度，并将其纳入输入代价；`r_jerk` 和 `r_dalpha` 是相邻输入差的软惩罚，并非相邻输出力或力矩的硬变化率限制。新参考不同可能使首步力快速改变；QP 的大小限制也不能限制每周期的变化速度。

当前参数中控制刷新为 100 Hz，而预测步长为 0.02 s。两种时间尺度和权重如何影响实际输出需要测量；不能仅凭频率差断言是根因。后续可对照参考连续化、权重调整及 QP 内的变化率约束，分别评估跟踪误差、求解失败和紧急停止行为。任何平滑措施都必须保留取消、过期和障碍失效时立即归零的保护。

### 4. 求解期间参考更新可能抑制一次输出

**状态：代码事实；运行时频率及其对尖峰的贡献待验证。**

`onOptPath` 收到参考时递增 `reference_version_`；[computeVelocityCommands](../../src/navigation/minco_controller/src/minco_mpc_controller.cpp) 在求解完成后比较版本，新参考在求解期间到达时会丢弃结果、输出零并重置求解器上次加速度。其目的是防止取消或参考替换后发布旧命令，但普通参考刷新与真正失效之间的行为仍需区分测量。应增加可观测的抑制原因，并覆盖同一轨迹刷新、新轨迹、BLOCK 和取消并发测试；不能简单移除版本检查。

### 5. 状态同步与延迟补偿

**状态：仿真延迟已测；对跟踪振荡的独立贡献待验证。**

控制状态的位置来自 Nav2 pose，速度和真实 yaw 来自 LIO；[solveDynamic](../../src/navigation/minco_controller/src/minco_mpc_controller.cpp) 在默认配置下使用固定 `control_delay_compensation=0.05 s`。此前 Release 仿真里程计延迟采样约 0.07–0.15 s，轮速融合默认关闭。时间差、执行器延迟及杆臂补偿都可能影响预测，不应把它们与轨迹切换混为同一个已证实根因。

仿真可用 `SIM_WHEEL_ODOM=1` 开启模拟轮速；该数据由仿真真值加噪生成，不代表实车反馈已验证。实车反馈需核对轴、方向、时间戳、质量以及断流回退。

### 6. 上限与模型标定

**状态：配置事实及实车风险。**

| 参数 | `sentry1.yaml` 实车默认 | `real` 仿真默认 |
| --- | ---: | ---: |
| 质量 | 28 kg | 17.737 kg |
| 偏航惯量 | 0.58 kg·m² | 0.7167 kg·m² |
| 平面合力上限 | 56 N | 56 N |
| 偏航力矩上限 | 2.32 N·m | 2.32 N·m |

`real` 模型的质量和惯量由 [real_robot.yaml](../../src/nav-simulation/sentry_simulation/config/real_robot.yaml) 覆盖，以匹配 CAD 仿真模型；力与力矩上限来自选定的导航参数文件。默认使用 `sentry1.yaml` 的 56 N 和 2.32 N·m；显式传入 `params_file:=` 时，可在该文件中自行设置力限。力上限作用于近似八边形内的平面合力，并受 `min(mu*g, max_force/mass)` 限制，并非 X/Y 各轴同时 ±56 N。

本节调整后的默认模型允许约 3.16 m/s² 的平移输入加速度和 3.24 rad/s² 的偏航角加速度。由于 CAD 仿真质量与实车默认质量不同，相同力限不代表相同的运动响应。上文已测现象使用的是当时的 100 N、100 N·m 仿真配置；新上限尚未完成严格的新旧闭环对照，不能直接视为尖峰已经消除。

调整后在隔离的 RMUC_2025 `real` 仿真中，从约 `(4.6, 7.3)` 向 `(4.6, 8.3)` 执行了一次短距离导航，结果为成功。采集的 517 条指令中，最大平面合力约 52.41 N、最大力矩绝对值 2.32 N·m；相邻接收样本的最大力向量变化约 46.87 N。结束后约 2 秒读取的 Gazebo 真值位置为 `(4.6495, 8.2547)`。这是单次冒烟测试，接收样本不保证覆盖每个控制周期；原始样本未归档，不能用它评估长期稳定性或证明峰值改善。

修改实车前应核对底盘惯量、摩擦、最大力矩、固件限幅、轮力分配、功率约束和坐标轴；切勿把仿真的 100 N·m 当成硬件安全值。

### 7. 重规划安全检查和实时预算

**状态：代码事实；最坏耗时和误停概率待验证。**

当前候选完整轨迹及连接段需通过碰撞检查；提交时也会重新检查保留轨迹。FSM 控制预算在 [sentry1.yaml](../../src/navigation/navi2_bringup/params/sentry1.yaml) 中为 5 ms，检查随轨迹长度和地图查询成本变化，预算耗尽可能触发既有撤销/回退。保留的历史片段也会接受安全检查，动态障碍出现在车辆已通过的片段时存在保守误停可能。需用动态障碍、长轨迹和高负载测试 p95/p99 与最坏耗时，不能仅凭短路线成功视为已覆盖。

## 观测与复现

1. 确认使用 Release 构建，消息、控制器和仿真包来自一致的工作区；不要混用旧版消息生成物。仿真入口：

   ```bash
   ./start_sim.sh robot_model:=real world:=rmuc_2025
   ```

2. 在加载同一工作区环境的终端启动 Foxglove Bridge：

   ```bash
   source /opt/ros/jazzy/setup.bash
   source install/setup.bash
   ros2 launch foxglove_bridge foxglove_bridge_launch.xml port:=8765
   ```

3. Plot 分开观察 `/chassis_cmd_mpc.wrench.force.x`、`.force.y` 与 `.torque.z`；前两项单位 N，后一项 N·m。图表应同步记录 `/opt_path`、`/aft_mapped_to_init`、`/sim/ground_truth/odom`、`/clock`、TF、控制器输出及动作结果。
4. 固定出生点、目标、模型、构建类型、参数和负载，采集多次往返。统计轨迹 ID 切换附近的 P/V/A 差、力差峰值与分位数、轨迹投影索引、里程计年龄、求解耗时和抑制原因；同时记录真值跟踪误差、速度、目标结果及终点停稳状态。使用相同坐标系和时间基准，保留原始 bag、配置和脚本版本。
5. 分别测试正常前进、急转/掉头、轨迹重叠、短余量、动态障碍、时钟跳变、传感器延迟和指令中断。对照实车前先验证所有安全失效动作与硬件参数。

现有 [controller_freshness_test.cpp](../../src/navigation/minco_controller/test/controller_freshness_test.cpp) 和 [test_planning_budget.cpp](../../src/navigation/minco_planner/test/test_planning_budget.cpp) 覆盖部分失效与连续性交接，但不等于完整闭环或动态障碍验收。现有 `scripts/check_sim_rolling_continuation.py` 部分统计仍使用旧的 `/sim/cmd_vel`，不能直接当作当前力输出的验收指标。
